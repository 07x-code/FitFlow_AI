# FitFlow AI 秋招分步开发计划

> 更新日期：2026-08-06  
> 项目主线：受控 Agent + 高并发后端。  
> 用途：作为后续开发、验收和秋招展示的唯一执行清单。

## 1. 项目定位

FitFlow AI 要做成一个安全、可追踪、能在并发压力下稳定运行的 AI 健身教练。

- 大模型负责理解问题、选择工具、解释数据和生成候选建议。
- 程序规则负责健康风险、权限、参数校验和数据写入边界。
- 用户负责批准或拒绝会改变正式计划的建议。
- 并发控制负责保护 LLM、数据库、Redis 和服务器资源。

一句话介绍：

> FitFlow AI 是一个基于 FastAPI、LangGraph 和大模型工具调用构建的健身 Agent，通过安全规则、人工审批、异步 I/O、限流和幂等机制，保证建议可控且服务在多人同时使用时保持稳定。

## 2. 范围说明

### 本项目重点

1. Agent 工具调用循环。
2. 上下文和用户记忆。
3. 确定性安全规则。
4. Proposal 人工审批。
5. Trace 和 Agent Eval。
6. 异步调用、连接池、限流和背压。
7. 幂等、重试、熔断和故障恢复。
8. 压测、部署和可复现演示。

### 秋招前不做 RAG

本项目不再开发以下内容：

- 文档导入和分块。
- Embedding。
- 向量数据库。
- 混合检索和 Rerank。
- 知识引用和 Recall@K 评测。

现有轻量知识检索不再扩建，也不作为项目亮点。清理时要同步删除无用工具注册、测试和配置，不能只删除文件。

结构化 Exercise Catalog 不属于 RAG。它只是普通业务数据，可在核心任务完成后作为 P1 增强项接入。

## 3. 当前基础和主要缺口

### 已有基础

- FastAPI 后端和 React PWA。
- 用户画像、训练计划、Proposal、训练记录、周报和 Coach API。
- Coach 已有“模型 → 工具 → Observation → 模型”的真实循环。
- 训练计划已有确定性的 LangGraph 工作流。
- 已有工具白名单、Pydantic 参数校验和最大调用轮数。
- `user_id` 由运行时注入，不由模型自行生成。
- 已有 Redis Working Memory、长期偏好和 Proposal 审批。
- 项目分层和后端自动化测试已有较好基础。

### 主要缺口

| 问题 | 影响 |
|---|---|
| 本轮高风险输入主要依赖模型提示词 | “我现在胸痛”仍可能进入普通回答 |
| 旧接口可以绕过 Proposal 保存计划 | 无法保证正式数据一定经过用户批准 |
| 多数前端页面仍使用 Mock 数据 | 无法演示完整产品闭环 |
| `X-User-ID` 由客户端填写 | 用户身份不可信 |
| 上下文主要靠手工拼接 | 历史变长后难控制 Token 和来源 |
| Agent 可调用的业务工具还不完整 | 无法根据真实训练情况进行分析 |
| 没有统一 Trace 和 Agent Eval | 出错后难定位，也无法量化效果 |
| LLM、LangGraph、Redis 和数据库以同步调用为主 | 请求多时容易耗尽线程 |
| SQLite 写并发能力有限 | 多人同时打卡或审批时容易锁冲突 |
| 没有限流、背压、幂等和熔断 | 流量或依赖故障可能拖垮服务 |

## 4. 最终业务流程

```text
用户登录
  ↓
限流、认证、Request ID
  ↓
检查本轮健康风险
  ↓
构建用户上下文
  ↓
Agent 判断是否调用工具
  ├─ 查询画像
  ├─ 查询正式计划
  ├─ 查询训练历史
  ├─ 查询本周报告
  └─ 创建调整 Proposal
  ↓
工具结果返回 Agent
  ↓
生成回答或候选建议
  ↓
需要写入正式计划时等待用户批准
  ↓
保存结果、Trace 和性能指标
```

## 7. 阶段 1：安全规则和写入边界

### 1.1 本轮输入安全门禁

请求进入 LLM 前，先用固定规则检查：

- 胸痛、呼吸困难和晕厥。
- 急性损伤、剧烈疼痛和疼痛持续加重。
- 极端减重和危险训练。
- 要求进行医疗诊断或绕过安全规则。

高风险请求直接返回安全建议，不执行普通工具和写入操作。模型可以润色文字，但不能改变风险等级。

### 1.2 关闭 Proposal 绕过路径

- 旧的计划草案接口只能创建 Proposal。
- 正式计划只能由状态为 `approved` 的 Proposal 生成。
- 审批和正式计划写入放进数据库事务。
- 使用条件更新保证一个 Proposal 只能批准一次。
- 模型可创建调整 Proposal，但不能直接修改正式计划。

### 1.3 安全测试

至少覆盖：

- 普通训练酸痛。
- 胸痛和呼吸困难。
- 急性损伤。
- 提示注入要求跳过安全规则。
- 越权读取其他用户数据。
- 重复或并发批准同一个 Proposal。

### 验收

- 高风险测试拦截率为 100%。
- 未批准 Proposal 无法改变正式计划。
- 并发审批同一个 Proposal 时只生成一个正式计划。

## 8. 阶段 2：真实产品闭环和用户认证

### 2.1 前端接入真实 API

按顺序替换 Mock 数据：

1. 用户画像和健康信息。
2. Proposal 生成、查看、批准和拒绝。
3. 正式训练计划。
4. 当日训练和每组打卡。
5. 训练历史。
6. 本周报告。
7. Coach 对话和工具执行状态。

### 2.2 用户认证

- 第一版使用简单 JWT 或签名 Demo Session。
- 后端从认证结果读取 `user_id`。
- 不再信任客户端直接提交的 `X-User-ID`。
- Repository 查询必须同时校验资源 ID 和 `user_id`。

### 2.3 修复闭环数据

- 周报只统计指定自然周。
- 训练记录必须绑定正式计划和训练日。
- 高疼痛或高疲劳打卡触发安全提醒。
- 写入操作返回稳定的业务 ID。
- 提供可重复导入的 Demo Seed 数据。

### 验收

- 清空数据库后，只通过 UI 能在 3～5 分钟内完成完整流程。
- 修改 Header 或资源 ID 不能读取其他用户数据。
- 核心页面不再依赖 `mock-data.ts`。

## 9. 阶段 3：Agent 核心能力

### 3.1 完善业务工具

优先提供以下模型可见工具：

| 工具 | 作用 | 权限 |
|---|---|---|
| `get_user_profile` | 查询用户画像和健康限制 | 只读 |
| `get_current_plan` | 查询当前正式计划 | 只读 |
| `get_workout_history` | 查询近期训练记录 | 只读 |
| `get_weekly_report` | 查询本周完成率、RPE 和疲劳 | 只读 |
| `get_active_proposal` | 查询等待处理的建议 | 只读 |
| `save_user_preference` | 保存用户明确确认的偏好 | 受控写入 |
| `create_adjustment_proposal` | 创建调整建议 | 只写 Proposal |

所有工具的 `user_id` 都由后端注入，模型不能传入其他用户身份。

### 3.2 ContextBuilder

不要把全部历史直接放进 Prompt。统一组装：

```text
固定安全规则
  → 可信运行时身份
  → 当前用户画像
  → 当前正式计划
  → 最近会话和摘要
  → 已确认的长期偏好
  → 本轮工具 Observation
```

每段上下文记录来源、可信等级、优先级、Token 数和截断原因。安全规则永远不能因为超出 Token 预算被删除。

### 3.3 记忆

- Working Memory 使用 Redis，按用户和会话隔离。
- 长期偏好记录来源和更新时间。
- 用户可以查看、修改和删除长期偏好。
- 用户明确输入优先于模型推断。
- 冲突内容不能静默覆盖。
- 敏感健康信息不能由模型自动写入长期记忆。

### 3.4 Agent 和工具预算

- 设置最大模型轮数。
- 设置最大工具调用次数。
- 设置单工具和整次请求超时。
- 设置 Token 预算。
- 同一轮重复工具调用去重。
- 仅对临时错误进行有限重试。
- 返回统一、脱敏的工具错误。
- 用户断开连接后取消未完成任务。

### 验收

- Coach 能根据真实画像、计划、训练历史和周报选择正确工具。
- 模型不能通过工具读取其他用户数据或直接修改正式计划。
- 调试结果能说明本轮提供了哪些上下文、为什么提供。
- 非法参数、空结果、超时和预算耗尽都有稳定响应。

## 10. 阶段 4：Trace 和 Agent Eval

### 4.1 Trace

每个 Agent 请求返回 `trace_id`，记录：

- 请求进入、排队和结束时间。
- 上下文片段及 Token 数。
- 每次模型调用的耗时、Token 和状态。
- 工具名称、输入摘要、输出摘要和错误。
- Guardrail 判断。
- 数据库和 Redis 耗时。
- Proposal 审批和最终写入结果。

日志不能保存密钥、密码和不必要的健康隐私。

### 4.2 Eval 数据集

建立 40～60 条固定样本，覆盖：

- 高风险输入。
- 工具选择。
- 工具参数生成。
- 多轮工具调用。
- 记忆召回和删除。
- 提示注入和跨用户访问。
- 模型、工具和数据库故障。
- 达到轮数、Token 和时间预算。

### 4.3 Eval 报告

一条命令生成 JSON 和 Markdown 报告。CI 使用 Fake Provider 运行稳定回归；真实模型评测单独运行，避免每次提交产生费用。

至少统计：

- 高风险拦截率。
- 工具选择准确率。
- 工具参数有效率。
- 最终任务完成率。
- 跨用户数据泄漏次数。
- 平均模型轮数、工具次数、Token 和耗时。

### 验收

- 100% 的 Agent 请求带有 `trace_id`。
- 高风险测试拦截率为 100%。
- 跨用户数据泄漏次数为 0。
- Prompt、模型或工具修改后能发现指标回退。

## 11. 阶段 5：高并发和稳定性

高并发不是多开几个 Worker。正确顺序是：减少阻塞、限制资源、保证写入正确，最后再扩容。

### 5.1 完整异步调用链

先改 Coach 这一条完整链路，再改其他接口：

```text
async FastAPI 路由
  → async Application Use Case
  → LangGraph ainvoke
  → async Tool
  → Async LLM / Redis / PostgreSQL
```

具体任务：

- DashScope 从同步 `urllib` 改为复用的 `httpx.AsyncClient`。
- LangGraph 从 `invoke()` 改为 `ainvoke()`。
- Redis 使用 `redis.asyncio.Redis`。
- 应用启动时创建客户端和连接池，关闭时统一释放。
- CPU 密集任务放入独立进程或后台 Worker。

只修改成 `async def` 不够，内部网络和数据库调用也必须是异步的。

### 5.2 PostgreSQL 和连接池

- 生产环境使用 PostgreSQL，SQLite 只用于本地简单运行或测试。
- 使用 SQLAlchemy Async 或 asyncpg。
- 使用 Alembic 管理数据库迁移。
- 配置连接池大小、等待超时和连接回收。
- 为用户、计划、状态和时间查询建立合适索引。
- Proposal 审批、计划切换和训练打卡使用事务。

### 5.3 限流和背压

- 设置可配置的全局 LLM 并发上限，例如先从 10 开始。
- 同一用户同时最多运行 1～2 个 Coach 请求。
- 限制等待队列长度。
- 限制请求体和上下文大小。
- 系统满载时快速返回 `429` 或 `503`。
- 返回 `Retry-After`，告诉客户端何时重试。

限流不是为了少服务用户，而是避免一批慢请求拖死所有请求。

### 5.4 幂等和数据一致性

以下操作增加 `Idempotency-Key` 或唯一业务键：

- Proposal 审批。
- 训练打卡。
- 周报生成。
- 调整 Proposal 创建。

优先使用数据库事务、唯一约束和条件更新。只有数据库无法解决时才考虑分布式锁。

### 5.5 超时、重试、熔断和降级

- 分开设置连接、读取、写入和连接池等待超时。
- 只重试网络超时、`429` 和部分 `5xx`。
- 使用指数退避和随机抖动。
- 连续失败达到阈值后暂时熔断模型调用。
- 模型不可用时，普通训练数据仍能查询和保存。
- 客户端断开后取消下游请求。

不能无条件重试写操作，否则可能生成重复数据。

### 5.6 Redis 和多实例

Redis 用于：

- Working Memory。
- 用户级和全局限流。
- 短期幂等记录。
- 分布式并发计数。
- 少量热点只读缓存。

正式业务数据仍以 PostgreSQL 为准。缓存键必须包含用户范围。

部署多个 Worker 或容器实例后，共享状态必须放入 PostgreSQL 或 Redis。`InMemoryWorkingMemoryStore` 只用于测试和本地开发。

### 5.7 健康检查和优雅关闭

- liveness 检查进程是否存活。
- readiness 检查 PostgreSQL 和 Redis 是否可用。
- 关闭服务时停止接收新请求，等待已有请求结束。
- 统一关闭 HTTP Client、Redis Client 和数据库连接池。

### 5.8 压测验收

Fake Provider 和真实模型必须分开压测：

| 场景 | 验收方式 |
|---|---|
| 普通查询接口 | 记录 100 并发下的 RPS、p95、p99 和错误率 |
| Fake Coach | 100 个并发会话，无线程池耗尽和跨用户记忆污染 |
| 真实 Coach | 不超过配置并发值；满载时快速返回 429/503，而不是大量 500 |
| 重复审批 | 20 个请求同时批准一个 Proposal，只生成一个正式计划 |
| 重复打卡 | 相同幂等键重复提交，只保存一条记录 |
| 依赖故障 | 模拟 LLM、Redis 和数据库故障，系统返回明确错误并能恢复 |

压测报告展示：

- 改造前后 RPS。
- p50、p95 和 p99。
- 错误率。
- 排队时间和活动 LLM 请求数。
- 数据库连接池占用。
- Redis 和数据库耗时。
- 限流、超时、重试和熔断次数。
- 单次请求 Token 和费用。

最终目标值在阶段 0 得到基线后确定，不能编造数据写进简历。

## 13. 阶段 7：有时间再做

### P1 增强项

- SSE 流式回答和工具执行进度。
- 将周报等离线任务放入后台队列。
- 接入结构化 Exercise Catalog，用 `exercise_id` 约束计划动作。
- 根据 Eval 结果增加简单 Router，将问题送到不同固定流程。
- 简单的性能监控页面。

互动 Coach 不要整段放入任务队列。队列适合离线任务，不适合需要立即响应的对话。

### P2 暂缓项

- RAG、Embedding 和向量数据库。
- 为了数量增加多个 Agent。
- Supervisor 和 Agent 自由协商。
- Reflection 自循环。
- MCP、A2A 和 ANP。
- Kafka、微服务和 Kubernetes。
- Agentic RL、SFT 和 GRPO。
- Neo4j 知识图谱。
- 摄像头姿态识别。

只有 Eval 证明单 Agent 无法完成任务时，才增加多 Agent。只有模块化单体出现明确瓶颈时，才拆微服务。
